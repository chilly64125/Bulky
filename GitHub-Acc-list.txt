Clarifying Development and Production Setup...

Short answer: they are two different servers in your setup.



http://localhost:5173/



Frontend dev server (Vite).

Serves the Vue SPA while you develop (HMR, fast rebuilds).

In dev it typically proxies API calls (e.g. /api/\*) to the backend so you can call the API without CORS issues.

Use this while actively editing frontend files.

http://localhost:5064/



Backend server (ASP.NET Core / Kestrel).

Hosts the API endpoints (e.g. /api/account/me, /api/admin/users) and in production serves the built SPA from wwwroot.

Also manages authentication, DB access, migrations, etc.

Key practical differences and notes:



Role in workflow:

Develop frontend → open 5173 (fast dev loop).

Test API or run full integrated server → use 5064 (runs backend).

Proxy / cookies:

Vite can proxy /api requests from 5173 to 5064 so the browser treats calls as same-origin. That makes cookie-based auth work during dev if axios.defaults.withCredentials = true and Vite proxy is configured.

If you open 5064 directly (production build served by backend), cookies are naturally same-origin.

Production vs dev:

Production flow: build SPA (npm run build), assets land in wwwroot, then the backend (5064) serves the static files + API.

Dev flow: run Vite (5173) + run backend (5064) simultaneously.

How to tell which one handled a request:

Open browser DevTools → Network → inspect request headers / response. Requests to /assets/\* are from Vite (5173) in dev; requests to /api/\* go to backend (5064) (or proxied to it).

Or curl each address: curl http://localhost:5173 vs curl http://localhost:5064/api/home.

q6: JWT (JSON Web Token) authentication

---------



JWT (JSON Web Token) authentication is a stateless, token-based method for securely transmitting information between a client and a server, commonly used for web applications and APIs. A JWT contains claims about a user or session, is digitally signed for integrity, and is sent with each request, eliminating the need for the server to store session state.  

How it works

Authentication: A user logs in, and the server authenticates them. 

Token issuance: After successful authentication, the server generates a JWT and sends it back to the client. 

Token structure: The token consists of three parts: a header, a payload (containing the claims), and a signature. 

Header: Contains information about the token type and the algorithm used for the signature. 

Payload: Contains the "claims," which are statements about the user and any other necessary metadata, such as a user ID, name, or permissions. 

Signature: A cryptographic signature is created using the header, payload, and a secret key. This is used to verify the token's authenticity and integrity. 

Subsequent requests: The client sends the JWT to the server with every subsequent request, typically in the Authorization header. 

Verification: The server uses its secret key to verify the signature on the incoming token. If the signature is valid, the server trusts the claims within the token and allows the request to proceed, without needing to look up session data in a database. 

Key benefits

Stateless: The server does not need to store session state, which is ideal for distributed systems and microservices. 

Scalable: Because the server doesn't need to maintain sessions, it can scale more easily. 

Compact: JWTs are a compact way to transmit information between parties, making them efficient to send in HTTP headers. 

Secure: JWTs are signed, ensuring that they have not been tampered with. This can be further secured by using HTTPS to prevent the token from being intercepted. 

Self-contained: All the necessary user information is in the token itself, reducing the need for database lookups on each request.

CSR (Client-Side Rendering)

--------------------------------------

CSR (Client-Side Rendering，客戶端渲染) 表示所有的頁面渲染 (render) 都透過瀏覽器端的 JavaScript 來完成。所有的邏輯、取資料、路由、template 都在客戶端處理。



CSR 可以用來建構時下流行的 SPA (Single Page Application，單頁式應用)。

CSR 的缺點主要有以下兩點：



載入速度通常較慢，尤其是在低階的行動裝置上。原因如前所述，因為 CSR 要等待 JavaScript 的下載及執行 render ，所以 CSR 頁面載入的前幾秒，頁面上會沒有東西或是只有一些骨架，使用者必須要等待一段時間才能看到頁面的內容，相對來說會是較差的使用者體驗。特別是在低階的行動裝置上，因為低階裝置的網路速度通常較慢，而且執行 JavaScript 會用到的 CPU 通常也較弱。

SEO 會較差，因為 CSR 的頁面對於爬蟲是比較不友善的。雖然爬蟲有辦法執行 JavaScript，但爬蟲也有一些 JavaScript render 頁面的限制。你可以用行動裝置相容性測試這個工具來測試一個 CSR 的頁面會如何被爬蟲 render 。



如圖所示，在 HTML 下載完之後，FCP (First Contentful Paint，使用者可以看到頁面上的重要內容的時間點) 會發生。值得注意的是，因為 CSR 的頁面通常只有一個根節點，所以這個時候畫面只會呈現一片空白。（當然也可以用一些 spinner 或是 skeleton 之類的東西來墊檔，相對來說使用體驗會稍好一點）



接下來會開始下載一大包 JavaScript bundle，下載完之後要解析並執行 JavaScript，最後才能 render 畫面。在完成這些事情之後，才達到了 TTI (Time-to-Interactive，使用者首次可以跟頁面互動的時間點)。在 TTI 之前，使用者點畫面上任何東西都不會有反應。



--------------------------------------

SSR (Server-Side Rendering)

--------------------------------------

SSR (Server-Side Rendering，伺服器端渲染) 表示伺服器收到使用者的請求之後，在伺服器端生成完整的 HTML。因為生成 HTML 的時候會在伺服器端先取得內部或外部 API 資料，所以相較於 CSR 從瀏覽器端取資料的模式，SSR 可以省去多次的來回往返。



在伺服器 render 完 HTML 後傳給使用者，這時候因為已經有完整的 HTML，所以很快就來到 FCP (First Contentful Paint，使用者首次看到頁面上重要內容的時間。)



接著要下載並且執行瀏覽器端互動所需要的 JavaScript，完成後就來到了 TTI (Time to Interactive，使用者首次可以跟頁面互動的時間點)。



SSR 的優缺點

SSR 的優點主要有以下幾點：



需要的 JavaScript 比較少，因此有較快的 TTI，可以較快開始互動，原因是相較於 CSR 所有 render 的邏輯都包含在 JavaScript 中，SSR 已經在伺服器端把 render 的工作做完了，SSR 方案中瀏覽器端需要的 JavaScript 理論上會比較少，所以會比較快達到 TTI。

有更多的 JS 預算可以留給其他第三方 JS 使用。

SEO 較佳，因為 SSR 產生的完整 HTML 可以很容易的被爬蟲解讀，不需要想辦法執行 JavaScript。SEO 也是大部分的人會考慮 SSR 方案的最主要原因之一。

SSR 的缺點主要有以下幾點：



較慢的 TTFB (Time to First Byte，從瀏覽頁面的動作開始到瀏覽器收到第一個 byte 所需要的時間)，因為在伺服器產生完整的 HTML 很花時間。如果同時有許多人造訪 server 造成負擔很重，或是有一些非常慢的 API，都有可能讓 server 的回應速度非常慢。

互動性體驗差，因為 SSR 的頁面在每次互動之間都要重新讀取頁面，這在使用體驗上就不如 CSR 的頁面順暢，也是現代 web app 大多數會採用 CSR 方案的主要原因。

Smoke test 基本資料

冒煙測試一詞是工程領域的專有名詞，在軟體與硬體中，分別有著不同的解釋與定義，這邊主要介紹的是軟體的部分，它是程序開發的一種測試方法，英文叫 Smoke testing， 有興趣看原文介紹可以看看冒煙測試(軟體) 維基百科說明。





用白話來解釋，冒煙測試，就是「將系統中的主要流程，裡面所用到的主要功能(必要功能、重要功能或你無法掌控的新功能)，優先串接起來進行測試，以確保用最少時間，檢核出該規劃的可行性」。



為什麼要做冒煙測試?

軟體開發，不論你是新軟體直接開發，還是新舊系統間的整合，在規劃上（很多時候是幾張圖紙）看似合理，但在實務執行層面往往因為：



系統規格與支援性

開發語言及版本

規劃人員的經驗與技術（最常見、最頭疼）

各合作廠商、單位間的技術落差

造成系統間銜接出問題，導致開發不順，或是一路毫無煞車的往懸崖開發，也因此，前期的在軟體開發、系統整合上，優先確認規劃可行性就變得非常重要。





冒煙測試的好處

前期進行冒煙測試，在系統整合與開發上非常常見與必要的，其好處在於：



直接驗證可行性：第一時間先確認路能不能通。

測試時間少：你不用進行全面測試，在開發初期針對重點進行即可。

避免開發翻車：系統開發最怕遇到，到後期才發現，系統之間無法對接的窘境，這將極大影響產品時程、成本。

因此，前期做冒煙測試，可協助專案人員與技術人員，在軟體開發上，有效管控可行性、時程、人力與成本。

&nbsp;toRefs converts each property of a reactive object into refs



...toRefs(reactiveState) converts each property of the reactive object into separate refs and the spread operator merges those refs into the object returned from setup so the template can access them as independent reactive bindings (e.g., you get a list ref available as list in the template). This prevents the common pitfall where destructuring a reactive object would break reactivity — toRefs preserves reactivity for each property when you unpack them.



Gotchas and notes:



The returned items are refs: in the template Vue auto‑unwraps them (use list), but in script you must use .value.

toRefs is shallow: the ref for list points at the array; nested objects inside the array remain the same references.

Spreading toRefs into the return can accidentally expose more internal state than needed or create naming collisions; prefer returning only the specific refs you need (or use toRef for a single property).

I’m diving into the concept of ...toRefs(reactiveState), which is about exposing reactiveState.list as refs. It's also important to remember that toRefs creates shallow refs, so with an array, the ref points to the array itself.

shallow copy:



// array shallow copy

const a = \[{ x: 1 }, { y: 2 }];

const b = \[...a];

b\[0].x = 9;       // a\[0].x is also 9 because inner objects are shared



// object shallow copy

const o1 = { a: { n: 1 }, b: 2 };

const o2 = { ...o1 };

o2.a.n = 5;       // o1.a.n is also 5





A shallow copy creates a new container (array or object) whose top-level elements/properties are copied, but if those elements are references (objects, arrays, functions), the references themselves are copied — not the nested data. So both original and copy point to the same nested objects; mutating a nested object in one affects the other.



Examples (JavaScript):



Contrast with deep copy: a deep copy recursively clones nested objects so the copy is completely independent. Ways to perform deep copies in JS:



structuredClone(obj) — modern, handles many types and preserves structure (recommended where available)

JSON.parse(JSON.stringify(obj)) — simple but loses functions, Dates, undefined, Maps, Sets, and fails on circular references

lodash.cloneDeep(obj) — reliable library solution

When to use which:



Use shallow copy (spread, slice, Object.assign) for immutably replacing top-level state or when nested objects should remain shared.

Use deep copy when you need full isolation of nested data (beware performance and type limitations).

Tip: prefer immutable updates (replace nested objects intentionally) instead of blindly deep-cloning large structures — it’s usually clearer and faster.

What is SPA?

==================



A SPA (Single‑Page Application) is a web application that loads a single HTML page and dynamically updates that page in the browser as the user interacts with the app. Instead of requesting full new HTML pages from the server for every navigation, the client-side JavaScript (frameworks like Vue, React, or Angular) swaps views/components and updates the URL via client-side routing to give the feel of multiple pages.



SPAs use client-side routing (e.g., Vue Router) to map URLs to components and often fetch data from APIs (JSON) rather than rendering pages on the server. This enables fast, app‑like navigation, fine-grained UI updates, and rich interactivity because only the necessary data and components are loaded or replaced.



Benefits include smoother navigation, fewer full-page reloads, and better perceived performance after the initial load. Common challenges are larger initial bundle size, SEO and crawlability (addressed with SSR or prerendering), browser history management, and the need for proper caching and code‑splitting to optimize load times.



To mitigate SPA limitations, teams often use server-side rendering (SSR) or hydration (Nuxt, Next), static site generation (SSG), route‑level code splitting, and well-configured metadata/SSR for SEO and social previews.

Kebab-case

-----------------------------------------------------------



Kebab-case is a naming convention where words are all lowercase and separated by hyphens (-).

In Vue templates, component tags use kebab-case.



For example, if you register a component as ErrorAlert (PascalCase) in your script, 

you use it in the template as <error-alert></error-alert> (kebab-case).



Why?

Vue automatically converts PascalCase component names to kebab-case when matching tags in the template. 

This is why <error-alert> refers to the ErrorAlert component.
